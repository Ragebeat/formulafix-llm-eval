# FormulaFix

壊れた Excel / Google スプレッドシートの数式(`#REF!`、`#VALUE!`、`#N/A`、循環参照、関数名のタイプミスなど)を貼り付けると、何が問題かを平易な言葉で説明し、修正した数式を返します。

このリポジトリは、小さなプロダクトの LLM 部分を Node/Next.js から Python/FastAPI に移植し、**計測**を中心に作り直したものです。正解診断つきのゴールデンデータセット、評価ハーネス、Postgres への実行結果の保存、git 管理されたプロンプトで構成されています。プロダクト自体は終了しました(表計算ソフトのベンダーが数式修正アシスタントを標準搭載したため)。このリポジトリが扱うのはエンジニアリングの部分です。

[RAG プロジェクト](https://github.com/Ragebeat/rag-japanese-labour-law)と同じ方針です。**あらゆる変更は固定データセット上の数値で裏づけ、成功基準は実行の前に書き、LLM の実行 2 回の比較を結論としない。**

> **判定精度は、ゴールデンセットで DeepSeek V4.1 Flash が 0.879、Qwen が 0.742。プロンプトを一度も調整していない検証用 35 件では 0.781 対 0.648。プロンプトの実験は 2 件とも実行間のばらつきの範囲に収まり、採用しませんでした。**
>
> **ステータス: 完了。** ハーネス、ゴールデンセット(80 件)、別個の検証セット(35 件)、ベースライン、事前登録した 2 つの実験(どちらも計測済みで、採用なし)、トレーシングが完成しています。サービスはデプロイしていません。このリポジトリは計測のためのものです。

80 件(dev 60 + held-out 20)。各行は 3 回の実行の平均で、括弧内は最小〜最大の幅です。あわせて、直前の構成のコントロール実行も行っています(温度が低くてもモデルの出力はぶれるため)。

最初の 2 行は、プロンプトもケースも同一で、モデルとプロバイダだけが違います。最良の構成は、元のプロンプトを使った DeepSeek の T=0.2 です。どちらの実験も、実行間のばらつきを超えてこれを上回ることはありませんでした(詳細は「うまくいかなかったこと」と [EXPERIMENTS.md](EXPERIMENTS.md) を参照)。

全実行で間違えるケース(系統的な誤り): Qwen は 80 件中 15 件、DeepSeek は 80 件中 6 件です。ロケールカテゴリの 3 件(g075、g077、g078)は両モデルとも間違えます。実行ごとに verdict や error type が変わるケース(ノイズ)は、Qwen が 18 件、DeepSeek が 9 件です。DeepSeek では、系統的な部分は verdict の誤りにして最大 7.5 ポイントなので、このセットではプロンプトの変更を verdict だけでノイズと区別するのはほぼ不可能です。改善の余地があるのは error type と修正の正しさです。

### 検証セット(プロンプトを一度も調整していない 35 件)

ゴールデンセットを凍結した後に作成し、そこで見つかった弱点(ロケール、ユーザーの不満の横にある正常な数式、正しいが珍しい構文、ひねりのある通常のエラー)を狙っています。ラベルは凍結前に人手で確認しました。議論の余地があるケースすべて、8 件のサンプル、Excel 2013 で試した 1 件が対象です。ロケールのケース 2 件は、ロケールを明示するよう書き直しました。verdict の正答率、3 回の平均、同じプロンプト、`temperature` 0.2:

| グループ(件数) | `qwen/qwen3.8-27b`(Groq) | `deepseek/deepseek-v4.1-flash`(DeepInfra fp8) |
|---|---|---|
| 全体 (35) | 0.648 (0.629–0.686) | 0.781 (0.771–0.800) |
| locale (12) | 0.861 | 0.861 |
| hidden_cause (8) | 0.458 | 0.500 |
| valid_unusual (8) | 0.417 | 0.875 |
| hidden_cause: 説明で原因を指摘 (8) | 0.792 | 0.917 |
| hidden_cause: 許容される対処を推奨 (8) | 0.375 | 0.458 |
| generic (7) | 0.762 | 0.857 |
| 安定性 | 0.829 | 0.943 |

モデル間の差は新しいデータでも維持されています(ゴールデンセットの 14 ポイントに対して 13 ポイントで、範囲は重なりません)。どちらのモデルもゴールデンセットより成績が下がっており(DeepSeek 0.879 → 0.781)、ゴールデンセットの数値は楽観的な側です。差はほぼ `valid_unusual` に集中しています。Qwen は、正しいが珍しい数式を壊れていると判定します。`locale` と `hidden_cause` は両モデルとも低く、同じケース(v010、v013、v017、v021、v034)で失敗しています。これはモデルではなく、課題とプロンプトのルールに原因があることを示します。8 件のグループでは 1 件が 12.5 ポイントに相当するため、グループごとの数値はあくまで目安です。`hidden_cause` では、verdict はプロダクトの実力を低く見せます。数式は正しく、本当の原因は別の場所にあるため、モデルは原因を指摘しながらも `ok` と答えることが多いのです。そこで別のモデルファミリーの審査員が説明を読み、原因が指摘されているか、許容される対処が推奨されているかを別々に採点します。(採点基準は、最初に見た統合版の後で書きました。統合版は名前より厳しいものでした。両方ともデータベースに残しています。)原因を指摘できた回答は DeepSeek で 0.917、Qwen で 0.792 ですが、許容される対処を推奨できたのは 0.458 と 0.375 にとどまります。モデルは何が悪いかをおおむね理解しています。弱いのはユーザーに何をすべきか伝える部分で、たとえばユーザーがすでに見つけた回避策を繰り返したり、正しい数式を書き換えたりします。

held-out のスコアは、どちらのモデルでも dev より高く(8〜10 ポイント)、held-out の絶対値は dev と比較できません。比較できるのは構成間の変化だけです。

### ゴールデンセットができる前

Node 版には 20 件のスクリプトがあり、期待値は緩いものでした(許容値のリスト、「チェックしない」項目)。プロンプトもこの同じ 20 件に合わせて調整されていました。現在のモデルで 3 回実行した結果は 17/20、16/20、16/20 でした(3 回目は 1 件が HTTP 502 で失敗)。#1、#2、#10 は毎回失敗し、#18 は実行によって変わりました。これは参考情報であり、ベースラインではありません。プロンプト調整の際にケースを見ているため、ゴールデンセットでは *dev* としてのみ残しています。

## アーキテクチャ

```
POST /analyze  {formula, context, dialect}
  ↓ 入力チェック(formula 3〜2000 文字、context ≤ 2000)
  ↓ prompts/<version>.txt のプロンプト(git 管理、sha256 を実行ごとに記録)
  ↓ OpenAI 互換の chat 呼び出し(現在は Groq、env で任意のプロバイダ)
  ↓ JSON 復元(Node 版と同じ) → Pydantic モデル
回答 {verdict, error_type, whats_broken, why, fixed_formula, what_changed, ...}
```

失敗は単に例外にするのではなく分類します。`rate_limited`(HTTP 429)、`timeout`、`api_error`、`invalid_json`、`truncated`(`max_tokens` で打ち切り)、`schema_violation` です。HTTP ステータスでインフラ側の失敗(429 / 504 / 502)を区別し、評価ではそれらを別々に保存するため、プロバイダのレート制限が誤答として数えられることはありません。インフラ側の失敗はリトライされ、再実行(`--resume`)もできます。形式の失敗はモデルの回答なのでそのまま残し、再抽選で形式失敗率を隠すことはしません。

評価は Postgres(Docker)に保存します。

| テーブル | 1 行が表すもの |
|---|---|
| `golden_cases` | ゴールデンセット(`data/golden_v1.jsonl`)または検証セット(`data/validation_v1.jsonl`)のケース。正のデータはファイル |
| `runs` | ケース全体を 1 回通した実行: モデル ID、温度、プロンプトのバージョンと sha256、ゴールデンセットの sha256 |
| `run_results` | 1 回の実行における 1 ケース: 回答、ステータス、レイテンシ、トークン、リトライ、採点、審査員の理由 |

2 つの構成の比較は、`run_results` に対する普通の SQL です。

### 意図的に移植しなかったもの

クォータ、認証、Stripe、Supabase、SEO ページ、法務ページ。これらはプロダクトの周辺部分であり、LLM の課題ではありません。

## 手法

### 最初の実行の前に固定したルール

- ゴールデンデータセットと指標は、コードや調整の**前**に作ります。成功基準は実行の前に書きます。
- LLM の実行 2 回の比較は結論ではありません。1 つの構成につき最低 3 回の実行と、旧構成のコントロール実行を行います。変更が採用されるのは、コントロール実行のばらつきを超えた場合だけです。
- ゴールデンセットの失敗に合わせたルールや辞書は書きません。成果が水増しされるためです。新しい変更は、調整で一切見ない **held-out** スライスで確認します。
- プロンプトの一般ルールを直すと、1 件を直して他を壊すことがよくあります。想定せず、測定します。
- 2 つ目のセット(検証セット、35 件)はゴールデンセットの凍結後に作成し、調整には使いません。誰も調整していないデータでも結果が成り立つかを確かめるためのものです。
- 実験は [EXPERIMENTS.md](EXPERIMENTS.md) に事前登録します。変更内容、仮説、採用基準、実行の順序(まず目的のあるいちばん安価なセットで変更が効くか確認し、その後にだけガード用の実行をする)を書きます。このファイルは一部ロシア語です。

### ゴールデンデータセット

80 件。`data/golden_v1.jsonl` として凍結(読み取り専用、実行ごとにファイルの sha256 を保存)。

| カテゴリ | 件数 |
|---|---|
| `#N/A` / `#REF!` / `#VALUE!` | 各 6 |
| `#NAME?` / `#DIV/0!` / 循環参照 | 各 5 |
| `#SPILL!` | 4 |
| 構文 | 7 |
| ロジック | 6 |
| 正しい数式(誤検知のチェック。うち 5 件は壊れて見えるが有効) | 15 |
| 数式ではないもの | 5 |
| ロケールと言語(`;` 区切り、キリル文字・日本語・中国語のシート名、`=` の欠落、全角の `＝`) | 10 |

Excel 48 件 / Google スプレッドシート 32 件。held-out は 20 件でカテゴリに分散。`debatable` のフラグ付きは 8 件。

各ケースには、期待される verdict、期待される error type、代替として許容される error type(モデルから見えないデータに診断が依存する場合)、修正のチェック方法があります。チェック方法は `any_of`(24 件: 正解修正のリスト)、`judge`(31 件: 文章の基準)、`none`(25 件)です。

**ラベルの作り方。** 数と現実性の要件(雑な数式、あいまいなユーザーのコンテキスト、原因についてのユーザーの誤った推測)を書いた仕様に基づき、より強力なモデル(Claude Opus)がチャットで生成・ラベル付けしました。評価対象のモデルは別ファミリーの Qwen です。その後、人が確認しました。`debatable` のケースすべて(当時 9 件)と、シード固定でランダムに選んだ 8 件、合計 17 件です。挙動が表計算アプリそのものの事実であるケース 3 件は、実際のアプリで試しました(2 件は Google スプレッドシート、1 件は Excel で確認できず)。その結果、4 件を変更しました(下記参照)。

### 指標

- **verdict**: 回答の verdict が期待値と一致する。
- **error type**: 壊れていると期待されるケースのうち、期待された型または代替の型と一致する。
- **fix correct**: `any_of` のケースは、まず正規化(空白、大文字小文字、`FALSE` ≡ `0`。引数の区切り文字は正規化*しない*。ロケールのケースでは区切り文字こそが修正)した上で正解と照合します。一致しなくても「誤り」ではなく、審査員に回します。`judge` のケースは必ず審査員に回します。
- **失敗した呼び出し**と**矛盾した回答**(たとえば `ok` と error type の併記)は、誤答とは別に集計します。
- **安定性**: すべての実行で verdict と error type が同じだったケースの割合。
- すべての数値を分母つきで、2 通りの見方で示します。*answered*(実際に回答があったもののうち)と *overall*(失敗した呼び出しは不正解として数える)です。

### 審査員

文字列照合で判定できない修正は、テスト対象とは**別のモデルファミリー**の `openai/gpt-oss-120b` が判定します(同じファミリーの審査員は同じ場所で盲目になるため)。審査員が見るのは、プロダクト、数式、コンテキスト、期待される診断、そして正解修正または文章の基準と、提案された数式のみです。モデルの説明は見ません。1 文の理由を判定ごとに保存しているので、サンプルを人が読んで確認できます。

**監査(13 件の判定を手で確認。Qwen 4 件、DeepSeek 9 件)。** 10 件は明らかに正しく、誤って「正解」とされたものはありませんでした。1 件は基準より厳しい判定でした(基準自体が許容している `INDEX(DATEVALUE(...),0)` を却下)。2 件は構造上判定できません。モデルが数式を変更せずに返し、対処を文章で述べた(「A:F の外に数式を移動する」)ケースで、基準は認めますが、数式しか見ない審査員は評価できません。これは 1 回の実行につき 55 件中 1〜3 件(2〜5%)で、両モデルに起こります。したがって `fix correct` は 1 回あたり約 1〜3 件分の下限値であり、構成間の比較には影響しません。この割合が変わった場合の対策は、数式が変更されていないときに限り説明も読む審査員です。

## うまくいかなかったこと

- **ベースラインのモデルがプロジェクトの途中で廃止された。** Groq は `qwen/qwen3-32b` を終了しました(2026 年 6 月 17 日に廃止を告知)。代替として案内された `qwen3.6-27b` は確認した時点ですでにモデル一覧になく、`qwen3.8-27b` は利用できました。「変更前」の数値は `qwen/qwen3.8-27b` で再計算する必要があり、古いテスト結果は履歴としてのみ扱います。正確なモデル ID と日付は実行ごとに記録しています。
- **無料枠の 1 分あたり出力トークン上限**(このモデルのオンデマンド枠で 1 分 1,000 トークン)により、`max_tokens=1024` を要求するリクエストは生成前に拒否されます。最初の Node 版の実行で発覚し、ゴールデンの実行速度を左右します(ケース間の待機、`Retry-After` に従うリトライ)。
- **修正の厳密な文字列照合は厳しすぎた。** 最初のスモーク実行で、正しい修正(`IF(A2:A="", "", VLOOKUP(...))`)が、正解側が空の結果を引数の省略で書いていたために誤りとされました。このケースのために正規化を直すことは、ゴールデンの失敗に合わせてルールを書くことになります。そこで原則を変え、24 件の `any_of` すべてについて、一致しないものは審査員に回すことにしました。これは全実行の指標を見る前に決めました。
- **4 件のラベルが誤り・あいまい・検証不能だった。** 凍結の*前*に修正しました。モデルから見えないユーザーの元の範囲を要求する修正チェック(g046)、「数式がテキストとして表示される」の複数の実際の原因のうち 1 つしか認めない修正チェック(g079)、Google スプレッドシートが無効な正規表現エラーとして報告するものに付けた `syntax` ラベル(期待される型を `#VALUE!` に変更、g044)、そして Excel で確認できなかった `#SPILL!` のケース(サイズが変動する `SEQUENCE`、g032)です。g032 の最初の代替案は既存のケースと同じ仕組みの重複でした(`#SPILL!` のケースを一覧して判明)。別の文書化された原因である、スピル範囲内の結合セルに差し替えました。
- **モデルが JSON の中で声に出して考えることがある。** あるケースで、モデルは有効な JSON オブジェクトを開いた後、`why` 文字列の中で自問自答(「Wait, if I change the formula to ...」)を続け、`max_tokens=1024` に達しました。閉じ括弧は来ず、回答は失われました。これは原因がはっきりした形式の失敗なので、意味不明な出力や誤答とは別に専用のステータス(プロバイダの `finish_reason` に基づく `truncated`)を付けています。実験の候補は、structured output / JSON モード、トークン予算の拡大、フィールド内で推論しないよう指示することです。いずれも他の変更と同様に測定します。
- **アグリゲータ経由のルーティングは、モデルのノイズに見えるノイズを加える。** 同じモデル ID への最初の 5 回のテストリクエストが、4 つの異なるプロバイダに処理されました(このモデルには fp4、fp8、不明な量子化のエンドポイントが約 30 あります)。現在は応答したプロバイダを結果ごとに保存し、実行は 1 つの fp8 エンドポイントに固定してフォールバックを無効にしています(モデル提供元自身のエンドポイントは、アカウントのデータポリシー上、有料モデルのプロンプトで学習される可能性があるため除外しました)。
- **`temperature` 0 は求めた安定性をもたらさず、誤りを固定した。** 実行前の基準: 成功 = 安定性 ≥ 0.95 かつ verdict 平均 ≥ 0.850。失敗 = 安定性 < 0.93 または verdict 平均 < 0.850。結果: 安定性 0.938(0.2 では 0.886)、verdict 平均 0.862(0.879 から低下)で、中間のため成功とは数えません。不安定なケースは 9 件から 5 件に減りましたが、毎回間違えるケースは 6 件から 10 件に増えました。0.2 ではモデルが偶然正解することもありましたが、0 では毎回間違えます。verdict と修正の正しさは実行間のばらつきを超えて改善しなかったため、デフォルトは 0.2 のままです。
- **ロケールに関するプロンプトのルール 1 つを書き換えても、約 1 ポイントしか上がらず、採用しなかった。** 元のルールは引数の区切りとして `,` と `;` の両方を受け入れるよう求めていましたが、これは「ロシア語版 Excel がカンマ区切りの数式を拒否する」と言うユーザーと矛盾します。そこで、区切り文字と小数点のカンマをロケールに結びつけるルールに置き換えました。基準は実行前に固定しました(`g077` と `v010` を含むロケールのケースを直し、他での悪化は 2 件以内)。結果: `v010` は毎回誤りから毎回正解になり、さらに 2 件のロケールのケースが改善しました。しかし変更のきっかけとなった `g077` は誤りのままでした。数式が明らかにカンマを使っているのに、モデルが「引数は `;` で区切られている」と述べるためで、これはルールでは直せない読み取りミスです。2 件が悪化しました(`g015`、`v019`)。うち 1 件は、モデルがロケールらしい入力に寛容になったためと考えられます。verdict 平均は、ゴールデンセットで 0.892(従来 0.879)、検証セットでは変化なしで、実行間のばらつきの範囲内です。モデルを入れ替えると verdict は 14 ポイント動きましたが、このルールでは約 1 ポイントでした。不採用です。Qwen での確認実行は、事前に決めた順序(まず目的を確認し、達成した場合にだけガード用の実行をする)に従い、省略しました。

## トレーシング

任意機能で、デフォルトはオフです。[Phoenix](https://github.com/Arize-ai/phoenix)(OTLP over HTTP を受け付けるバージョンならどれでも)を起動した状態で、`.env` に `PHOENIX_COLLECTOR_ENDPOINT=http://127.0.0.1:6006` を設定します。

```powershell
uv run uvicorn api:app --app-dir src --port 8000          # API は全リクエストをトレースする
uv run python src/run_golden.py --label x --trace          # ゴールデン実行は全ケースをトレースする
```

1 リクエストにつき 1 トレースで、`analyze` スパン(数式、コンテキスト、verdict、ステータス)の中に `llm` スパン(モデル、プロバイダ、トークン数、finish reason、コスト、実際のメッセージ)が入ります。トレースは Phoenix のプロジェクト `formulafix`(`PHOENIX_PROJECT_NAME` で変更可)に、他のプロジェクトと並んで保存されます。ゴールデン実行は 1 つの Phoenix セッション(`run-<id>`)になり、`formulafix.case_id` で 1 つのケースを全実行にわたって探せます。モデルの形式失敗(`invalid_json`、`truncated`、`schema_violation`)は ERROR スパンになります。エンドポイントがない場合や `--trace` がない場合は何も送信されず、評価も変わりません。

![Phoenix の 1 トレース: analyze スパンの中に llm スパン](docs/img/phoenix-trace.png)

## 注意点

- 80 件: 1 件は 1.25 ポイントに相当します。信頼区間はなく、差は繰り返し実行のばらつきと比べて判断します。
- ゴールデンセットは LLM がラベル付けし、人による確認は一部のみです。ラベル付けした側と審査員(どちらも LLM)が共有する盲点を排除することはできません。
- 審査員はセカンドオピニオンであり、真実ではありません。手作業の監査は 13 件の判定だけで、厳しめに判定する傾向が見える程度であり、誤り率を示すには足りません。
- 検証セットは 35 件で、4 グループ(7〜12 件)に分かれます。グループ内では 1 件が 8〜12 ポイントに相当するため、グループごとの数値は目安です。ラベルは人手で確認しましたが、1 件(v012)は議論の余地が残り、v035 は Excel 2013 でしか確認していません。
- `hidden_cause` の採点基準(原因の指摘 / 許容される対処)は、最初の統合版を見た後で書きました。両方を保存しています。審査員が説明を読むのはこのグループだけです。
- `fix correct` は下限値です(審査員の監査を参照)。
- Groq の「preview」付きモデルは短期間で削除されることがあるため、結果はモデル ID と日付に紐づきます。

## 実行方法

必要なもの: Python 3.14、[uv](https://docs.astral.sh/uv/)、Docker。

```
cp .env.example .env                 # POSTGRES_PASSWORD と LLM_API_KEY を設定
uv sync
docker compose up -d --wait
uv run python src/db_init.py
uv run python src/load_golden.py     # ゴールデンセットを検証して読み込む

uv run uvicorn api:app --app-dir src --port 8000      # http://localhost:8000/docs

uv run python src/run_golden.py --label baseline --repeat 3
uv run python src/score.py  --label baseline
uv run python src/judge.py  --label baseline
uv run python src/report.py --label baseline

# 検証セットと hidden_cause の採点基準
uv run python src/load_golden.py --set validation
uv run python src/run_golden.py --label baseline-val --split validation --repeat 3
uv run python src/score.py  --label baseline-val
uv run python src/judge.py  --label baseline-val
uv run python src/judge_cause.py --label baseline-val --rubric v2
```

審査員は、`JUDGE_BASE_URL` / `JUDGE_API_KEY` / `JUDGE_MODEL` が設定されていればそれを使い、なければ `LLM_BASE_URL` / `LLM_API_KEY` のエンドポイントを使います。テスト対象のモデルが別のプロバイダにある場合は、`ENV_FILE` を指定せずに実行してください。`ENV_FILE=.env.openrouter` でプロバイダのプロファイルを選べます。

Windows と Docker の組み合わせでは、`localhost` ではなく `127.0.0.1` に接続してください(コードはデフォルトでそうしています)。`localhost` はまず IPv6 で試されますが、公開ポートは IPv4 のみのため、スクリプトの起動 1 回に 0.35 秒ではなく 130 秒かかっていました。

`tools/check_prompt_parity.py` は、Python 版のプロンプトが Node 版と一語一句同じであることを検証します。
